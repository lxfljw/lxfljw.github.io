### **1、dev-flow MCP 研发提效平台** <span class="time">有赞科技 · 2025.01 - 2026.03</span>

**项目背景**：线上问题排查需在**日志、数据库、接口、发布**等多个内部系统间频繁切换，操作均在浏览器中进行，上下文割裂、路径长，严重拉低排障与发布效率。

**项目描述**：主导设计并开发团队内 **dev-flow MCP Server**，将**项目发布、天网日志查询、数据库查询、接口调用**等原本需在浏览器手动操作的能力，封装为 AI 助手可直接调用的 **MCP Tool**；通过 **browser-cookie3** 读取本地浏览器的 SSO Cookie 并注入请求，开发者无需手动传入任何 Token；工具在 **Cursor** 等 IDE 中串联使用，配合 **OpenSpec** 做需求任务协作。

**业务价值**：排查链路从「手动开多个 Tab → 浏览器操作 → 来回切换」压缩为**在 IDE 内一条指令完成**；日志、数据、代码改动可在同一上下文中流转，缩短排障与发布闭环。

**项目职责**：主导 MCP Server 架构设计与核心工具开发；实现基于 browser-cookie3 的登录态读取与注入模块；设计各工具的输入/输出协议，完成内部系统对接与联调；沉淀团队使用规范与 Skill 文档。

**技术要点**：
- **MCP Server**：基于 MCP 协议设计工具集，Tool 粒度对齐单一职责，供 AI 助手按步骤编排调用
- **无感登录**：通过 **browser-cookie3** 读取本地浏览器（Chrome）的 Cookie 存储，提取目标系统登录凭据并自动注入请求头；Cookie 不存在或已失效时，自动跳转至系统 SSO 页面，等待用户完成认证后恢复任务继续执行，整个过程对调用方透明
- **能力模块**：发布（触发构建/部署流程）、天网日志（按 TraceId/时间/服务名查询）、DB 查询（只读，防误操作）、接口调用（带鉴权头自动注入）
- **OpenSpec**：与需求任务协作结合，提升跨角色交付效率

### **2、用户权益次数打标** <span class="time">有赞科技 · 2025.10 - 2025.11</span>

**项目背景**：业务需要按用户权益使用情况做**用户打标**（如分层、运营触达），并处理**过期权益**后的标签刷新；历史权益与用户数持续增长，若按「全量重扫历史权益次数」设计，任务规模随时间线性膨胀，不可持续。

**项目难点**：打标依赖累计次数，过期事件发生时需重算关联用户的次数并刷新标签；若每次都扫全量历史数据，DB 压力与任务耗时无法控制。方案上以**昨日过期**为时间窗口圈定受影响用户，增量处理替代全量扫历史。

**项目描述**：主导规则打标链路在 Java 侧的设计与落地；支持按**累计次数阈值或次数区间**命中规则打标；过期侧由**每日定时任务**驱动，按**昨日过期**维度圈选用户集；处理时**每批拉取 5000 条**，处理完成后继续下一批，控制单次 DB 压力；联调与线上问题排查。

**业务价值**：规则可配置，过期侧标签按日更新；以增量时间窗口替代全量扫历史，DB 与任务压力可控。

**技术要点**：
- **昨日过期窗口**：MySQL 按过期时间圈选昨日过期记录，与全量历史解耦，任务规模稳定可控
- **游标分批**：按主键游标翻页，每批取 5000 条，处理完推进 cursor 再取下一批；避免全量加载导致的内存与 DB 压力
- **批次内聚合去重**：每批数据 GROUP BY userId 统计累计次数，同一用户多条记录自动合并为一条结果，命中阈值/区间规则后发消息触发打标，不重复发送
- **扩展性**：若单线程处理量不足，可在应用层按 `userId % N` 分片，起 N 个并行 worker 各自跑游标分批，N 可配置，核心逻辑不变

<br>

### **3、商家预约日历状态缓存改造** <span class="time">有赞科技 · 2025.02 - 2025.03</span>

**项目背景**：日历需展示商家**未来约 30 天**左右每日是否约满；**预约下单链路已有**，原先列表/日历若频繁按天算约满，读路径压力大。

**项目描述**：**预约能力不改造**，通过 **NSQ** 订阅**预约成功**等相关 Topic；结合 **TSP** 定时任务，对需重算的**商家 + 本地日**做**去重**与**防抖**（合并短时间内的多次触发），再**拉库重算**约满并写入 **Redis**（约 30 天窗口内）；日历查询优先读 Redis。

**业务价值**：约满状态与预约落库解耦为**异步刷新**，读路径走缓存，减轻日历接口重复计算；预约仍以原有服务为准，本项只维护**展示用派生状态**。

**项目亮点**：
- **读写分离**：预约核心不改，**NSQ + TSP** 异步维护约满，不阻塞下单链路。
- **口径可讲清**：重算**以 DB 为准**，Redis 只存展示；**全量重算**而非缓存内加减。
- **去重与防抖**：**TSP** 对「商家 + 本地日」合并短时多次触发，减少同一日**重复拉库重算**。

**项目职责**：参与 **NSQ** 消费与 **TSP** 定时任务下的重算触发、去重/防抖策略、Redis Key 设计与异常兜底，Java 侧实现与联调。

**技术要点**：
- **NSQ** 与预约下单解耦；**Channel** 按团队约定配置，失败与重试按现有规范兜底
- **TSP** 定时任务：对「商家 + 日期」维度做**去重 / 防抖**，避免短时大量消息导致同一日**重复全量重算**
- **Redis** 仅存约满结果；**重算以 DB 为准**（查库得到当日预约与营业时间等），再写入；键维度：`商家 + 日期`；解析**受影响本地日**（注意跨日）
- 全量重算式更新；可配合 **TTL** 或定时纠偏

<br>
