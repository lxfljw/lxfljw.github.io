# 秒杀系统设计总结

## 1. 秒杀系统背景

秒杀业务特点：

- 瞬时高并发
- 请求量远大于库存量
- 热点商品访问集中
- 库存不能超卖
- 订单不能重复创建
- 系统需要保证稳定性

例如：

```
商品库存：100

用户请求：100万人

目标：

- 100个订单成功
- 系统不崩
- 不出现超卖
- 用户体验可接受
```

---

# 2. 秒杀系统核心目标

## 2.1 抗高并发

不能让所有请求直接进入业务服务。

解决：

- CDN
- 网关限流
- 排队
- MQ削峰

---

## 2.2 防止超卖

多个用户同时购买：

```
库存 = 1

用户A读取库存
用户B读取库存

都认为可以买

导致：

库存 = -1
```

解决：

- Redis库存
- Lua原子扣减
- 数据库最终校验

---

## 2.3 保证最终一致性

例如：

```
Redis扣库存成功

↓

订单创建失败
```

导致：

```
库存少了
订单不存在
```

解决：

- 消息可靠投递
- 补偿机制
- 库存流水

---

# 4. 流量入口层设计

# 4.1 CDN静态化

## 作用

减少后端压力。

例如：

商品详情：

- 图片
- 描述
- 活动规则

提前放 CDN。

流程：

```
用户访问页面

↓

CDN返回静态内容

↓

不经过业务服务器
```

---

# 4.2 网关/Nginx限流

## 为什么需要限流？

假设：

```
10亿请求
```

不可能全部进入：

- Spring Boot
- Redis
- MySQL

所以：

先过滤。

---

## 常见方式

### IP限流

例如：

```
同一个IP：

1秒超过100次

拒绝
```

问题：

- NAT误伤
- 代理绕过

所以只能辅助。

---

### 用户限流

根据：

```
userId
```

限制请求频率。

例如：

```
一个用户：

10秒最多5次
```

---

### QPS限流

限制系统整体入口：

例如：

```
系统最大：

10万QPS

超过直接拒绝
```

---

# 5. 用户防刷设计

## 5.1 一个用户只能购买一次

不能依赖前端。

前端：

```
按钮置灰
```

只是体验。

后端必须控制。

---

## Redis防重复

Key：

```
seckill:user:{userId}:{activityId}
```

请求：

```
SETNX
```

第一次：

```
成功
```

继续。

第二次：

```
失败
```

拒绝。

---

## 数据库最终保证

数据库建立唯一索引：

```sql
UNIQUE(user_id, activity_id)
```

作用：

防止：

- 并发请求
- MQ重复消费
- 服务重试

---

# 5.2 设备风控

防止：

一个人注册多个账号。

识别：

- deviceId
- 浏览器指纹
- Cookie
- IP
- User-Agent

例如：

```
100个账号

↓

同一个设备

↓

风险提高
```

# 5.3 行为风控

```

↓

停留

↓

支付
```

```

↓
```

# 6. Token准入控制

## Token是什么？

Token本质：

> 用户进入秒杀链路的资格凭证。

不是库存。

---

## 错误理解

```
库存100

↓

发100个token

↓

100个人购买
```

这种属于资源预分配。

---

## 常见设计

Token：

控制：

```
谁可以进入
```

库存：

控制：

```
谁最终可以买
```

两个职责分离。

---

# 7. Redis库存设计

## 7.1 为什么库存放Redis？

MySQL：

```
大量请求

↓

数据库压力巨大
```

Redis：

内存操作。

速度快。

---

## 7.2 库存预热

活动开始前：

MySQL：

```
stock = 100
```

同步：

Redis：

```
stock = 100
```

---

# 8. Redis Lua扣库存

## 错误方式

```java
stock = get()

if(stock > 0){

    stock--

}
```

并发：

```
用户A读取100

用户B读取100

都扣减

```

可能超卖。

---

## Lua保证原子性

逻辑：

```
判断库存

↓

扣减库存

↓

返回结果
```

三个动作不可拆分。

---

示例：

```lua
if stock > 0 then

    stock = stock - 1

    return success

else

    return fail

end
```

---

# 9. MQ削峰

## 为什么使用MQ？

Redis扣库存成功后：

不要同步创建订单。

否则：

大量请求：

```
同时打订单服务
```

---

## 异步流程

```
Redis扣库存成功

↓

发送MQ

↓

订单服务消费

↓

创建订单
```

---

## 好处

### 削峰

瞬时：

```
10万请求
```

变成：

```
每秒消费5000
```

---

### 服务解耦

秒杀服务：

不关心订单内部实现。

---

# 10. MQ消息可靠性

## 问题

情况：

```
Redis扣库存成功

↓

MQ发送失败
```

结果：

```
库存减少

订单不存在
```

---

# 解决：本地消息表

数据库：

```sql
message_record

id

business_id

status

retry_count

create_time
```

状态：

```
INIT

SUCCESS

FAIL
```

---

流程：

```
扣库存成功

↓

写消息记录

↓

发送MQ

↓

成功更新状态

↓

失败等待重试
```

---

# 11. MQ重复消费

## 为什么会重复？

例如：

```
MQ发送成功

↓

服务宕机

↓

状态没有更新

↓

重新发送
```

产生：

两条消息。

---

## 解决：消费者幂等

方式：

数据库唯一约束：

```sql
UNIQUE(user_id, activity_id)
```

第一次：

创建订单。

第二次：

发现重复。

直接返回成功。

---

# 12. 订单创建设计

## 不建议直接修改通用订单表

原因：

订单中心是公共能力。

秒杀规则属于业务。

---

## 方案1：秒杀订单表

例如：

```sql
seckill_order

id

user_id

activity_id

order_id

status
```

唯一：

```sql
UNIQUE(user_id, activity_id)
```

---

## 方案2：订单业务字段

订单：

```sql
order

order_id

user_id

biz_type

biz_id
```

唯一：

```sql
UNIQUE(user_id,biz_type,biz_id)
```

# 15. 面试回答模板

秒杀系统设计核心是：

> 通过分层削峰、流量控制、缓存承载热点请求、异步化处理以及最终一致性保证，实现高并发情况下系统稳定。

具体：

1. 入口通过 CDN、网关限流过滤大量无效请求；
2. 秒杀服务使用 Redis 保存热点库存，并通过 Lua 保证库存扣减原子性；
3. 成功请求进入 MQ 异步创建订单，实现削峰；
4. 通过唯一索引和幂等机制防止重复购买；
5. 通过消息重试、库存流水、补偿任务保证最终一致性。

---

# 16. 核心思想总结

| 模块       | 解决问题         |
| ---------- | ---------------- |
| CDN        | 减少静态请求压力 |
| 限流       | 防止系统被打爆   |
| Token      | 控制进入资格     |
| Redis      | 承载热点库存     |
| Lua        | 防止超卖         |
| MQ         | 削峰填谷         |
| 唯一索引   | 保证幂等         |
| 本地消息表 | 保证消息可靠     |
| 补偿机制   | 保证最终一致     |

一句话：

> 秒杀不是让所有人都成功，而是让系统在巨大流量冲击下稳定运行，并保证最终库存和订单正确。
