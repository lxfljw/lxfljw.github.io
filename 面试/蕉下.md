## 面试题 & 标准答案

### 1. Vue 响应式：`a.b.c` 与 `ref` / `shallowRef`

**题目**：嵌套对象 `a.b.c` 赋值后视图会不会更新？`ref` 和 `shallowRef` 有什么区别？

**当时短板**：只写了代码草稿，没讲清触发条件和适用场景。

**标准答案**：

结论先说：`ref` 包的对象是深层响应式，改 `a.b.c` 会更新；`shallowRef` 只跟踪 `.value` 引用变化，直接改内层属性不会触发更新。

```json
{
  "a": {
    "b": {
      "c": 1
    }
  }
}
```

- `const obj = ref({ a: { b: { c: 1 } } })`：`obj.value.a.b.c = 2` 会触发更新，因为 Proxy 递归代理了嵌套对象。
- `const obj = shallowRef({ a: { b: { c: 1 } } })`：改内层不会更新；需要整体替换 `obj.value = { ... }`，或对嵌套层再用 `reactive`，或用 `triggerRef(obj)` 手动触发。
- 选型：`ref` 适合中小型、需要深度追踪的数据；`shallowRef` 适合大对象、外部状态（图表实例、第三方 SDK），避免深度代理带来的性能和意外触发。

**可追问 & 答案**：

1. **`watch` 默认浅还是深？**
   - 监听 **`reactive` 对象**：默认**深监听**，改嵌套属性会触发。
   - 监听 **`ref` 包的对象**：`ref` 内部会转响应式，改 `ref.value.xxx` 也会触发。
   - 监听 **getter**（`() => obj.xxx`）或**普通对象引用**：默认**浅监听**，只有返回值引用变了才触发；要盯嵌套变化需加 `{ deep: true }`。
   - 口诀：源本身是响应式对象 → 深；getter / 手动返回的对象 → 浅，要 deep 自己开。

2. **`triggerRef` 什么时候用？**
   - 只配合 **`shallowRef`** 用。你改了 `shallowRef.value` 的内部属性，引用没变、视图不更新时，调 `triggerRef(ref)` 手动通知依赖刷新。
   - 典型场景：第三方实例（ECharts、地图 SDK）内部改了状态；或你刻意用 shallowRef 避深代理，又不想整体 `obj.value = { ... }` 替换时。

3. **大列表每项用 `ref` 还是 `shallowRef`？**
   - **不要**给几千项每项都套 `ref`，依赖追踪和内存开销都很大。
   - 常规做法：外层一个 `ref([])` / `reactive([])` 管整表，项是普通对象；局部更新用 `list[i] = newItem` 或 `splice` 替换单项。
   - 项很大、更新频繁、又不想深代理：外层 `shallowRef(list)`，改某项后 `list.value[i] = xxx` 再 `triggerRef(list)`，或直接 `list.value = [...list.value]` 换引用。
   - 需要每项深度 `v-model` 绑定（如动态表单）：用 `reactive` 数组 + 项为 `reactive` 对象，项数可控（几十级）时再用；大列表配合虚拟滚动，只渲染可视区。

### 2. 小程序优化：首屏 / 分包上限 / 构建速度

**题目**：代码量大、分包数量和体积都到上限，首页慢、构建慢，怎么优化？

**当时短板**：说了主包瘦身、懒加载方向，但缺具体上限数字和优先级。

**标准答案**：

微信限制先摆出来：主包 ≤ 2M，单个分包 ≤ 2M，所有分包总和 ≤ 20M，分包数量 ≤ 20 个。到上限说明不是单点问题，要「减体积 + 拆结构 + 提构建」一起做。

**（1）首页加载**

- 主包极简化：只留 `app`、首页骨架、TabBar 必需资源、登录/启动逻辑；其余页面全部下沉分包。
- 按需加载：非首屏组件、重型 SDK、图表库放分包或异步分包；开启「按需注入」「用时注入」减少启动代码量。
- 渲染优化：减少首屏 `setData` 数据量和频率；图片走 CDN + 合适格式；骨架屏先出结构。
- 预下载：对高频跳转分包配置 `preloadRule`，在空闲时预拉取。

**（2）代码到上限**

- 盘点主包：把非 Tab 页、低频业务、大组件迁出；公共组件按使用频率拆到对应分包，避免全塞主包。
- 独立分包：登录、活动页等可独立启动的场景用独立分包，不占主包体积。
- 减依赖：审计 `node_modules` 和静态资源，删无用代码；图片/字体压缩；能走 npm 的组件库不要整包拷贝。
- 实在不够：评估 H5 承载低频页、或拆成多个小程序。

**（3）构建速度**

- 缓存：CI 缓存 `node_modules`、构建产物；本地开启 Webpack/Vite 持久化缓存。
- 并行：多线程压缩、esbuild/swc 替代 babel 转译（视框架支持）；分包可并行构建再合并。
- 索引优化：原生组件/自定义组件建立索引，减少全量扫描（对应你提到的原生索引思路）。
- 工程治理：统一 lockfile、pnpm 硬链接减安装时间——这块我在有赞做过 Yarn → pnpm 迁移，CI 耗时明显下降。

**可追问 & 答案**：

1. **独立分包和普通分包区别？**
   - **普通分包**：必须先进主包（或已被下载的分包），再 `navigateTo` 进分包页；分包可以依赖主包里的公共资源。
   - **独立分包**：可以**不下载主包直接启动**（扫码、分享链接直开活动页）；**不能依赖主包 JS**，自己的组件、工具要自给自足。
   - 选型：登录页、营销活动页、低频落地页 → 独立分包减主包体积；Tab 页、强依赖公共逻辑的业务 → 普通分包。

2. **异步分包怎么配？**
   - 场景：A 分包里的组件/JS 被 B 分包或主包引用，但不想打进主包体积。
   - 配置：在 `app.json` 的 `subPackages` 里给对应分包加 `"independent": false`（默认），再用 **分包异步化**——在 `app.json` 声明 `"lazyCodeLoading": "requiredComponents"`（按需注入），跨分包引用时用 `require.async('../subPkg/utils.js')` 异步加载。
   - 效果：引用方先渲染，目标分包代码运行时拉取，把依赖从主包挪走。
   - 注意：异步加载有回调时序，要做好 loading / 失败兜底；循环依赖要避免。

3. **`setData` 性能瓶颈怎么排查？**
   - **看体积**：单次 `setData` 数据 > 64KB（经验值）就容易卡；合并多次调用，只传变化字段，不要整个 `this.data` 重传。
   - **看频率**：滚动、拖拽里高频 setData → 加节流；能算的逻辑放 WXS / 纯渲染层处理，少跨逻辑层通信。
   - **看工具**：开发者工具 → 性能 → 查看 `setData` 调用次数、耗时、数据量；Audits 扫启动和渲染。
   - **看结构**：列表只更新变化项的 index 字段，别 `setData({ list: 全新数组 })` 触发整表 diff；大列表上虚拟列表 / 分页。
   - **看渲染**：减少不必要的自定义组件嵌套层级；`hidden` vs `wx:if` 按场景选，避免隐藏节点仍参与布局。

### 3. AI 多项目协作：如何减少人工干预

**题目**：多个项目、多个需求并行用 AI 开发，怎么减少一直盯着 AI 改？

**当时短板**：流程讲得对，但和 MCP 落地的结合不够具体，缺少自己项目的例子。

**标准答案**：

核心观点：AI 提效不是「多写代码」，是**减少人的决策次数**。你一直在介入，通常是在替 AI 做三件事——拆任务、做判断、做验收。要把这三件事系统化。

**为什么总要人介入（4 点）**

1. 需求是自然语言，边界不清，AI 不知道改哪些文件、不动哪些。
2. 没有任务拆分，一个需求一坨 prompt，无法并行。
3. 没有状态管理，做到一半不知道哪些子任务完成。
4. 没有验收标准，不知道对不对，只能问人。

**目标流程**

```
需求 → 结构化 Spec → 任务拆分 → 并行执行 → 自动 Review → CI 验证 → 合并/回滚
```

人只留在三个节点：需求确认（一次）、关键风险审批（偶尔）、最终结果验收。

```text
          +-------------+
需求 ---> | Planner AI  |
          +-------------+
                 |
        task decomposition
                 |
   +-------------+-------------+
   |             |             |
worker-1     worker-2     worker-3
   |             |             |
   +-------------+-------------+
                 |
          Reviewer AI
                 |
           CI / merge
                 |
            production
```

**落地手段**

- **Spec 先行**：用 OpenSpec 等把需求结构化成可验收的条目，AI 按 spec 改，review 也按 spec 对。
- **Planner 拆任务**：按仓库/模块/文件边界拆成可并行子任务，避免一个 agent 扫全仓。
- **Reviewer + CI 兜底**：自动 code review + 跑 lint/test/build，不达标回滚重跑，不等人盯。
- **MCP 接能力**：我在有赞做的 dev-flow MCP 就是这个思路——把日志、DB、接口、发布封成 Tool，AI 在 IDE 内按 Skill 编排调用，不用人来回切 Tab 喂上下文。多项目场景可拆成：task MCP（接需求）、repo MCP（改代码）、review MCP（审查）、ci MCP（验证）。

**可追问 & 答案**：

1. **多 repo 上下文怎么隔离？**
   - **工作区隔离**：每个 repo 独立 worktree / 独立目录，agent 一次只开一个 repo 的上下文，不混文件树。
   - **任务级上下文**：Planner 拆任务时带 `repo` / `branch` / `scope`（目录白名单），worker 只能读写 scope 内文件。
   - **MCP Tool 隔离**：repo MCP 按仓库注册 Tool，调用时显式传 `repoId`；日志、CI、发布 Tool 也按项目切配置，避免 A 项目的 trace 查到 B 项目。
   - **记忆隔离**：不把 A 项目业务规则写进 B 项目的 Skill；公共规范放 shared Skill，业务 Skill 按仓库拆分。
   - 并行时：一 repo 一 agent，合并前由 orchestrator 统一排依赖顺序（先公共库后业务仓）。

2. **验收失败怎么回滚？**
   - **代码层**：每个子任务走独立分支 / PR，CI 红灯不合并；失败自动 `git revert` 或关闭 PR，主分支保持绿。
   - **任务层**：子任务状态机 `pending → running → review → done / failed`，failed 的只重跑该任务，不从头来。
   - **发布层**：若有预发验证，失败走发布系统回滚到上一版本（我这边 dev-flow MCP 的发布 Tool 可以触发构建，回滚同样走流水线）。
   - **AI 层**：Reviewer 不通过 → 把失败原因 + diff 喂回 worker 重试，设最大重试次数，超限再人工介入。
   - 原则：**小步提交、可自动撤销**；永远不让未验收的改动直接进 main。

3. **Spec 谁维护、怎么防漂移？task 怎么关联 commit？**
   - **谁维护**：需求方 / PM 出原始需求，研发落成 **OpenSpec / 结构化 Spec**（requirement + 验收场景）；**`spec.md` 写「要什么」**，**`tasks.md` 写「怎么做」**，改代码前 spec 先定，改完一起 PR。
   - **spec id 不进业务代码**：关联放在变更目录的 `tasks.md`（traceability 台账），每条 task 绑 `req`、`scope`、`files`、`tests`；agent 做完回写，**禁止在 `src/` 里写 task id**。
   - **commit 记在 task，不写在 spec.md**：`spec.md` 是长期规范，不绑某次 git SHA；task 完成后把 commit 列表追加到 `tasks.md`，commit message 带 `[T{n}]`。
   - **防漂移**：
     - requirement 可测试：Given / When / Then 或 checklist，CI 能验的自动验。
     - PR 对照 `tasks.md` checklist 审，不只审风格。
     - 实现与 spec 不一致 → 补代码或先改 spec，**禁止 silent drift**。
   - **上下文怎么减**：一个需求通常 **一个 agent 会话** 顺序做；对话里只加载当前 task 的 req + scope，全文在 `tasks.md` / `spec.md` 文件里，agent 按需 read，工具大结果写文件不写 chat。

   **`tasks.md` 示例（task ↔ commit）**：

   ```markdown
   # Tasks: add-login-validation

   ## T1 手机号格式校验
   - 状态：done
   - req：SHALL validate phone format on login submit
   - scope：src/pages/login/**
   - files：src/pages/login/validate.ts, LoginForm.vue
   - tests：tests/login/phone.test.ts
   - commits：
     - a3f91c2 feat(login): add phone validator [T1]
     - b8e204f test(login): add phone cases [T1]
   - done：校验 + 单测通过

   ## T2 错误提示
   - 状态：done
   - req：SHALL show inline error when invalid
   - commits：
     - c17d4a9 feat(login): show error message [T2]

   ## T3 记住密码
   - 状态：in_progress
   - commits：
     - d42e8b1 wip(login): remember-me checkbox [T3]  # 进行中，完成后继续追加
   ```

   ```text
   spec requirement → tasks.md 的 req 字段 → task T1/T2 → commits 列表 → git 历史
   ```
